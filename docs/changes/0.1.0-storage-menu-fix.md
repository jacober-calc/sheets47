# 0.1.0 storage and system-menu repair

15 November 2026. Version remains **0.1.0**; this repairs the first build without
adding spreadsheet features. Use the replacement binary hash in the
[validation record](../validation-0.1.0.md) to distinguish builds.

## Report and cause

The user tested on **DM32**: the graphical worksheet, demo, and new worksheet
worked, but Save reported inaccessible storage. FILE → SETUP consequently did
not open DMCP. SHIFT+0 also failed, leaving SHIFT displayed. Firmware/keymap and
the binary hash on the device were not supplied. The report is retained in
[machine-readable form](../validation/2026-11-15-dm32-report.json).

The platform adapter incorrectly treated the firmware's normally disabled
application write flag as a disk fault. It checked `sys_is_disk_write_enable()`
without ever calling `sys_disk_write_enable(1)`. That prevented both creation
of `/SHEETS47` and normal saves. This was a platform integration bug missed by
the original host filesystem tests.

Both setup entry points also required a successful save whenever the workbook
was dirty. That made a disk failure block access to system and USB settings.
The logical SDK SHIFT+0 sequence already decoded correctly; the original
implementation silently ignored unmapped positive key codes and left SHIFT
latched. The exact physical-key reason for the reported persistent indicator
is not established without a device retest.

## Changes

- Directory creation and every file write explicitly enable firmware write
  access, close/flush the file, and restore the previous protection state on
  success and failure. No persistent permission change or file deletion occurs.
- Directory and write failures expose the operation and numeric firmware error.
- SETUP still attempts to save dirty work. A failure now offers **CONTINUE** or
  **CANCEL**, warning that SETUP can reset the application. Continue opens DMCP
  without repeating the failed save; Cancel retains the worksheet. Returning
  displays an unsaved reminder. This does not promise RAM survives USB/reset.
- Key releases preserve SHIFT until the next press. Unmapped presses consume
  SHIFT and identify their SDK key code on the device, with FILE → SETUP as the
  alternate path. No alternate physical-key mapping is guessed or installed.
- The real device file, input, and menu adapters now run in host regression
  tests against the pinned SDK declarations and stub firmware services.

Tests cover normally protected storage, exclusive creation, short writes,
failed open/write/close, unavailable disk, prior protection restoration, actual
adapter save/load, explicit FILE → SAVE, both setup entry points, confirmation,
cancel, successful retry, and entry to DMCP with no open file or write permission.
They also exercise SHIFT/zero with and without an intervening release, and
preserve unsaved data after a failed Save. This does not emulate the DM32's
physical keyboard scanner, firmware filesystem, USB, or sleep behavior.

## DM32 retest

1. Load the rebuilt `sheets47.pg5` from the current package.
2. Use FILE → DEMO, FILE → SAVE. Expect `SAVED /SHEETS47` and no dirty asterisk.
3. Change B2 to 5, commit with ENTER, then Save. Expect total 23.50. OPEN should
   recover that value; after a normal restart the saved worksheet should load.
4. Try SHIFT, release, 0, and separately FILE → SETUP. Both should open the same
   settings menu. Return and check that the worksheet is restored.
5. If storage fails, record the full operation/error code. SETUP → CONTINUE
   must still reach DMCP. If SHIFT+0 reports `Unmapped key N`, record N and the
   installed keymap/firmware. Finish or cancel an editor draft before SETUP.

No device firmware update or keymap replacement is required by this repair.
The original executable and validation evidence are retained locally under
`build/qualification/2026-11-15-before-storage-menu-fix/`. Current sources,
tests, and this report are reviewable in Git; no commit or push is performed
by the build/package tools.

Reference: [SwissMicros SDK key-event example](https://github.com/swissmicros/SDK5demo/blob/master/src/main.c)
and [system key-table documentation](https://technical.swissmicros.com/dmcp/devel/dmcp_devel_manual/).
Disk write-service declarations are in the pinned `third_party/dmcp5/dmcp/dmcp.h`;
read-only Brainbox Chess47/Nav47 examples corroborate scoped write enable.
